ABSTRACT

On university campuses, peer-to-peer collaboration and informal student services—ranging from lab assignment debugging, web design for college festivals, and LaTeX research paper formatting to technical workshops—occur predominantly through unstructured social media channels such as WhatsApp and Telegram. This ad-hoc environment introduces significant enterprise risks: absence of identity verification, rampant payment defaults ("ghosting"), lack of portfolio credibility, and zero recourse for resolving disputes.

CampusGigs is an enterprise-grade, closed-loop campus micro-marketplace developed to solve these fundamental challenges. Engineered using modern web paradigms with React 19, TypeScript, Vite, Express 5, and PostgreSQL, the system delivers mathematical transaction guarantees and trust via five core pillars:

  • Domain-Gated Authentication & RBAC: Strict @thapar.edu credentials enforcement with support for Undergraduate (Years 1–4), Postgraduate (M.Tech, PhD), and Faculty tiers.
  • Atomic Financial Escrow: An automated double-entry ledger running within PostgreSQL ACID transactions (BEGIN ... COMMIT / ROLLBACK). Credits are frozen in escrow upon task assignment and released strictly upon approved work submission, eliminating payment ghosting.
  • Multi-Archetype Campus Workflows: Tailored lifecycles supporting Freelance Gigs, Faculty-Led Workshops (with capacity caps), Academic Projects, and 1-on-1 Mentorships.
  • Content-Based Recommendation Engine: A multi-factor algorithmic recommendation layer ranking opportunities by student experience level, department, and category completion history.
  • Production-Grade Verification: Validated by 79 automated Vitest test suites (100% pass rate), 65% initial frontend bundle size reduction via dynamic route code-splitting, zero package vulnerabilities, and connection pool management.

This report details the architectural design, entity-relationship modeling, component implementation, security considerations, and rigorous testing methodologies that govern CampusGigs.

Chapter 1: Introduction

1.1 Introduction to the Project

In higher education institutions such as Thapar Institute of Engineering & Technology, thousands of students engage in academic and technical peer transactions daily. These micro-engagements include semester project programming, banner graphics for technical societies, MATLAB simulation assistance, LaTeX formatting for research publications, and campus technical workshops.

Historically, these activities have been coordinated over decentralized, informal chat channels (WhatsApp batches, Telegram groups, Discord servers). While easily accessible, these platforms lack the enterprise structural mechanics required to sustain fair peer commerce. CampusGigs bridges this void by providing a unified, secure campus SaaS micro-marketplace. The application replaces cash friction with an internal, closed-loop soft-credit economy, enabling students to gain real-world freelancing competence, verifiable reputation metrics, and portfolio accreditation within a university boundary.

1.2 Problem Statement

The existing unstructured model of student freelancing exhibits several critical vulnerabilities:

  1. Payment Default and Ghosting: Student workers often spend dozens of hours completing project deliverables only for the client to disappear without payment. Conversely, posters risk advancing payments to peers who fail to deliver on schedule.
  2. Identity Impersonation and Security Risks: Anyone with a group invite link can solicit services, exposing students to external scams, academic dishonesty rings, and malicious payload distribution.
  3. Information Asymmetry: Posters have no reliable means to verify a peer's competence prior to task assignment, resulting in wasted time and sub-par submissions.
  4. Inefficient Event Management: Faculty and student societies lack a centralized registry to schedule skill-development workshops, publish prerequisites, track capacity limits, and verify attendee participation.

1.3 Objectives of the Project

The primary functional and non-functional goals of CampusGigs are:

  • Zero-Default Financial Escrow: Implement an atomic ledger engine ensuring 100% of assigned tasks have funds locked upfront, releasing them only upon mutual agreement or formal dispute settlement.
  • Closed-Loop Campus RBAC: Enforce institutional authenticity by restricting registration to @thapar.edu credentials while assigning specific operational privileges based on academic standing (Undergraduate, Postgraduate, Faculty).
  • Diverse Campus Workflows: Provide native architectural modeling for Gigs, Workshops, Collaborative Projects, and Mentorships.
  • Personalized Recommendation Algorithm: Eliminate the cold-start problem through content-based matching of listings against student profiles and category history.
  • Enterprise Performance and Reliability: Deliver sub-second page loads, responsive card layouts, strict schema validation, and comprehensive automated test validation.

1.4 Scope of the Project

The functional perimeter of the project includes:

  • User Identity Management: User registration, credential hashing with bcrypt, JWT token pair issuance, refresh cookie rotation, and onboarding profile setup.
  • Marketplace Discovery: Public-first feed allowing unauthenticated browsing, faceted keyword search with SQL wildcard escaping, and category/difficulty filtering.
  • Task State Machine: Strict enforcement of task states: OPEN → ASSIGNED → SUBMITTED → COMPLETED / DISPUTED / CANCELLED.
  • Capacity-Controlled Workshops: Faculty workshop hosting with venue selection, start/end date validation, and strict applicant capacity barriers.
  • Trust & Moderation Suite: Mutual two-way reviews (1–5 stars), proof-of-work uploads, dispute arbitration queues, and administrative account suspensions with instant token revocation.

2.6 Module Description

  • Authentication Module: Intercepts all requests, validates Bearer JWT signatures in memory, verifies role authorization, and provides silent refresh cookie rotation.
  • Listing & Workshop Module: Enforces chronological constraints (ends_at > starts_at) and restricts workshop host rights to verified faculty.
  • Escrow Engine Module: Maintains financial invariants, locking poster rows with FOR UPDATE to eliminate concurrency double-spending race conditions.
  • Recommendation Engine: Implements composite scoring using profile experience levels, interest categories, recency decay, and historical category completion frequency.
  • Moderation & Safety Module: Enables neutral arbitration of disputed funds and immediate account suspensions with active token destruction.

3.4 Implementation of Major Modules

1. Atomic Escrow Engine Implementation

Listing 3.2: Atomic Escrow Hold Function (backend/src/utils/wallet.ts)
export async function holdEscrow(
  client: PoolClient,
  opts: { taskId: string; posterId: string; amount: number }
) {
  if (opts.amount <= 0) return

  // Row-level lock prevents concurrent double-spending race conditions
  const { rows } = await client.query(
    "SELECT wallet_balance FROM profiles WHERE id = $1 FOR UPDATE",
    [opts.posterId]
  )
  const balance = Number(rows[0]?.wallet_balance ?? 0)
  if (balance < opts.amount) {
    throw new AppError(400, 'INSUFFICIENT_FUNDS', 'Insufficient credit balance for escrow hold')
  }

  // Deduct poster balance
  await client.query(
    "UPDATE profiles SET wallet_balance = wallet_balance - $1 WHERE id = $2",
    [opts.amount, opts.posterId]
  )

  // Append double-entry ledger record
  await client.query(
    "INSERT INTO transactions (task_id, from_user, amount, type) VALUES ($1, $2, $3, 'escrow_hold')",
    [opts.taskId, opts.posterId, opts.amount]
  )
}

3.5 Exception Handling & Security Sanitization

  • Postgres Constraint Interception: Internal database codes such as 23505 (unique violation) are cleanly translated into HTTP 409 Conflict without exposing internal table schemas or raw SQL queries.
  • Path Traversal Prevention: In uploads.routes.ts, uploaded file names are sanitized with path.basename() and regex filtering: name.replace(/[^a-zA-Z0-9._-]/g, ''), preventing directory escape attacks.
  • SQL Wildcard Sanitization: In tasks.routes.ts, user search inputs escape %, _, and \ characters to defend against wildcard injection.
  • Cookie Path Scoping: The HTTP-only refresh token cookie is scoped strictly to path: '/api/v1/auth', minimizing CSRF and cross-route exposure.

3.6 Data Structures & State Management Usage

On the client side, TanStack Query v5 manages an in-memory asynchronous cache with reactive cache invalidation. When mutations (such as accepting an applicant or marking a task complete) succeed, the query keys ['task'], ['wallet'], and ['my-tasks'] are marked stale, triggering seamless background refetches.
